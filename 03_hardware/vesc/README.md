# VESC — my unit's configuration

What is here is **my inverter's configuration**, not the tool or the firmware. It is a hardware
source of truth: the `.m` files in `04_model/params/` are derived from these files.

| File | What it is |
|---|---|
| `MOTOR_1.9.xml` | `mcconf` — motor configuration exported from VESC Tool (2026-08-10) |
| `MOTOR_1.9_app.xml` | `appconf` — application configuration (throttle ADC, CAN) |
| `screenshots/foc-detection_2026-07-29.png` | FOC detection, first run (at 97.85 A) |
| `screenshots/usb-serial-error_2026-08-10.png` | The USB drop under load. **Not a detection** |
| `reference/appconf_default.h` | Firmware defaults, auto-generated by VESC Tool |
| `reference/mcconf_default.h` | Same, motor side |

The two `.h` files are the reference an XML is read against: they say what each field means
and what its factory value is.

## The heavy stuff is here, but outside Git

So the VESC doesn't have to be looked for in two places, the third-party software lives in
this same folder — with a leading `_` and in `.gitignore`:

| Folder | What | Size |
|---|---|---|
| `_firmware/` | VESC firmware source code (bldc, **FW 7.01**) | 219 MB |
| `_tool/` | `vesc_tool_6.06.exe`, the installer | 166 MB |

The rule doesn't change: **what I write is versioned, not what I download.** It is the same
boundary as between `.venv/` and my Python scripts.

`motor-parameters.md` cites the firmware by file and line with links to `_firmware/`. On a new
machine, clone [`vedderb/bldc`](https://github.com/vedderb/bldc) there for them to resolve;
the line numbers are from **FW 7.01**.

The VESC Tool test logs are **not** here: they are data, and go to
`06_data/<date>_<test>/`.
